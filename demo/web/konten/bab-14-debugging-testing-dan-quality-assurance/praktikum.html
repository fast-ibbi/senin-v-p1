Praktikum Bab 14 — Unit Test, Console, dan Checklist

Empat pekerjaan: menjalankan 13 unit test fungsi validasi, menelusuri data dengan tiga jenis pesan console, memeriksa endpoint dari terminal sebelum menyentuh aplikasi, lalu mengisi checklist pengujian minimal lima kasus uji. Tanpa satu pun npm install untuk bagian test.

Tujuan praktikum

Setelah menyelesaikan praktikum ini, kamu mampu:

  1. menjalankan unit test fungsi validasi dengan node:test dan membaca laporannya;
  2. menggunakan console.log, console.warn, dan console.table untuk menelusuri data;
  3. memeriksa endpoint API dari terminal, termasuk membaca kegagalannya;
  4. mengisi checklist testing berdasarkan hasil pengujian aplikasi sendiri.

Kebutuhan

  • Node.js LTS versi 22 atau lebih baru — cek dengan node --version. Di bawah Node 18 modul node:test belum tersedia; lihat Troubleshooting.
  • Project hasil Bab 10 (sudah terhubung API) atau project Bab 8 (formulir + validasi). Bila keduanya belum ada, folder kerja kosong dengan dua berkas dari subbab 14.4 sudah cukup.
  • Backend buku berjalan: cd backend && npm install && npm start (lihat Bab 10) — hanya diperlukan untuk langkah 4 dan 5.
  • Terminal atau Command Prompt, dan editor teks.

Persiapan

  1. Buat folder praktikum14 di lokasi kerja.
  2. Di dalamnya buat struktur folder utils/ dan __tests__/. Folder __tests__ diawali dua garis bawah — konvensi yang dikenali banyak alat pengujian.
  3. Salin utils/validators.js dari bagian 3 ke praktikum14/utils/validators.js, dan __tests__/validators.test.js ke praktikum14/__tests__/validators.test.js.
  4. Pastikan terminal berada di dalam praktikum14, bukan di dalam __tests__, karena path relatif ../utils/validators.js dihitung dari folder __tests__.

Langkah kerja

  1. Jalankan test lewat eksekusi langsung: node __tests__/validators.test.js. Amati keluaran TAP yang tercetak.
  2. Jalankan mode deteksi otomatis: node --test. Bandingkan ringkasannya dengan langkah 1.
  3. Buat berkas console-demo.js (kode di bawah), jalankan node console-demo.js, dan amati perbedaan tampilan console.log, console.warn, serta console.table.
  4. Uji endpoint dari terminal: pastikan backend berjalan, lalu jalankan perintah node -e "fetch(...)" di bawah. Catat status yang tercetak.
  5. Simulasikan kegagalan: hentikan server backend, ulangi langkah 4, lalu perhatikan pesan error dari blok catch.
  6. Buka project Expo kamu (hasil Bab 8 atau Bab 10), jalankan npx expo start, lalu tekan m untuk menu developer, r untuk reload, dan j untuk membuka debugger. Temukan pesan console.log aplikasimu di sana.
  7. Dengan project yang sama, buka React Native DevTools dan tab Network, lalu lakukan satu operasi yang memanggil API. Amati satu permintaan fetch, statusnya, dan isi responsnya.
  8. Terakhir, isi checklist pada subbab 14.7 untuk aplikasimu sendiri: jalankan minimal 5 kasus uji, tulis hasil aktual, dan beri status.

Kode: perintah terminal

Penjelasan kode

console-demo.js memakai kelima data mahasiswa baku buku ini (Bab 4–10). Tiga hal yang perlu diperhatikan. Pertama, setiap panggilan console diberi label teks, misalnya 'Jumlah data mahasiswa:', sehingga saat banyak log bercampur di terminal kamu tetap tahu arti tiap baris. Kedua, console.warn dipakai untuk kondisi abnormal — ada mahasiswa ber-IPK di bawah 3.0 — sehingga tampil mencolok dan tidak terlewat. Ketiga, console.table mengubah larik objek menjadi tabel berkolom NIM, Nama, Prodi, dan IPK: cara tercepat memverifikasi apakah datanya benar-benar sampai dan berbentuk seperti dugaan.

Operator spread ... (Bab 3) meneruskan setiap IPK ke Math.max, sedangkan filter lalu map memilih nama mahasiswa yang IPK-nya di bawah 3.0. Berkas test bekerja dengan pola satu test satu perilaku: strictEqual memeriksa kesetaraan nilai, notStrictEqual memeriksa ketidaksamaan, dan deepStrictEqual membandingkan struktur objek secara menyeluruh. Desain itu membuat laporan kegagalan langsung menunjuk aturan validasi yang dilanggar — baik aturan itu memang salah maupun test-nya yang salah menduga.

Perintah fetch pada langkah 4 menjalankan permintaan yang sama dengan aplikasi. r.status mencetak kode status HTTP (200 sukses, 404 tidak ditemukan, 500 error server — artinya dijelaskan di Bab 10). Bila respons sukses, console.table menampilkan data; bila server mati atau alamatnya salah, blok catch mencetak penyebabnya. Perintah ini dijalankan dari folder mana pun, selama server backend hidup di port 3000.

Hasil yang diharapkan

  1. Langkah 1–2: seluruh 13 test lulus; keluaran diakhiri ringkasan pass 13 dan fail 0 dalam format TAP.
  2. Langkah 3: terminal menampilkan tiga jenis pesan — dua baris console.log, satu baris peringatan console.warn, dan satu tabel 5 baris × 4 kolom dari console.table.
  3. Langkah 4: tercetak Status: 200 dan tabel data mahasiswa.
  4. Langkah 5: server dimatikan, blok catch mencetak pesan kegagalan, dan aplikasimu tetap aman karena tidak ikut dijalankan.
  5. Langkah 6–7: menu developer muncul di emulator, r memuat ulang aplikasi, dan tab Network menampilkan permintaan fetch beserta statusnya.
  6. Langkah 8: checklist terisi minimal 5 baris dengan hasil aktual dan status; bila ada kasus gagal, perbaiki lalu uji ulang.

Salah paham

Kegagalan lingkungan bukan kegagalan logika. “Unknown file extension” atau “Cannot find module” belum membuktikan test-mu salah; keduanya masalah versi dan path. Sebaliknya, laporan yang hijau juga bukan bukti aplikasi benar — 13 test yang lulus hanya menyatakan aturan validasi terverifikasi, bukan bahwa aplikasimu layak dirilis. Dua kekeliruan ini sama-sama mahal: yang pertama menghabiskan waktu memperbaiki kode yang tidak rusak, yang kedua membuatmu melewatkan bug yang nyata.

Yang harus teramati

  • node --test menutup dengan ringkasan pass 13 dan fail 0 — bukti terukur bahwa seluruh kasus uji pernah dijalankan.
  • console.table mencetak tabel lima baris untuk data mahasiswa, lengkap dengan kolom NIM, Nama, Prodi, dan IPK.
  • curl atau fetch menjawab status 200 selama server backend hidup.
  • Server dimatikan: blok catch mencetak pesan kegagalan, bukan aplikasi berhenti.
  • Checklist pengujianmu sendiri terisi minimal 5 kasus uji dengan hasil aktual dan status.
Laporan yang baik melampirkan keluaran terminal dan tabel checklist, bukan hanya tulisan “berhasil”.

  3. Sifat apa pada fungsi murni yang membuatnya ideal untuk unit test?
  4. Apa beda utama unit testing dan integration testing?
Kunci kuis kilat
  1. Debugging — bukan testing, dan bukan quality assurance.
  2. console.table — menyusun array objek menjadi kolom rapi, sehingga nilai yang salah langsung terlihat.
  3. Deterministik: hasilnya hanya ditentukan argumennya, sehingga masukan yang sama selalu memberi keluaran yang sama.
  4. Tingkat cakupannya: satu unit yang dipisahkan dari sekitarnya versus kerja sama antarbagian (state, fetch, dan tampilan).

Ringkasan bab

  1. Debugging mencari dan memperbaiki; testing memeriksa secara terencana; QA mencegah sejak awal lewat standar, checklist, dan prosedur.
  2. console.log untuk nilai biasa, console.warn untuk kondisi mencurigakan, console.table untuk data tabel; label pada setiap log membuat pesan mudah ditelusuri.
  3. React Native DevTools menyediakan breakpoint dan tab Network; React DevTools menampilkan pohon komponen dan state; kombinasi tombol m/r/j bersifat sensitif versi.
  4. Enam error React Native yang umum masing-masing punya penyebab dan solusi khas; RedBox selalu memuat lokasi baris kesalahan.
  5. Uji endpoint dengan curl, browser, atau fetch bawaan Node sebelum mengintegrasikannya; perhatikan alamat localhost, 10.0.2.2, dan IP LAN (Bab 10).
  6. Unit test menguji satu fungsi secara terisolasi; fungsi murni adalah target termudah karena deterministik.
  7. node:test menjalankan unit test tanpa dependency tambahan; piramida testing menaruh banyak unit test di dasar dan sedikit end-to-end test di puncak.
  8. Manual testing dipandu checklist; usability testing mengamati sekitar lima pengguna nyata untuk menilai kemudahan pemakaian.
  9. Checklist testing adalah produk QA yang hidup: setiap bug yang diperbaiki menjadi kasus uji permanen (test case regression).
