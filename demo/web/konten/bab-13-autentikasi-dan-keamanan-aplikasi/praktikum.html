Praktikum Bab 13 — Login, Token, dan Logout

Satu pekerjaan besar yang terdiri atas sembilan berkas: membangun lapisan autentikasi pada Aplikasi Manajemen Data Mahasiswa dari Bab 10. Daftarkan akun, masuk, simpan token di SecureStore, lindungi halaman daftar mahasiswa, lalu keluar.

Tujuan praktikum

Setelah menyelesaikan praktikum ini, kamu mampu:

  1. memasang expo-secure-store dengan perintah Expo yang benar;
  2. membungkus tiga fungsi penyimpanan aman dalam satu berkas utilitas;
  3. memusatkan pemanggilan API pada satu berkas yang menyisipkan header Authorization;
  4. menyusun penyedia autentikasi dengan tiga status: memuat, masuk, keluar;
  5. melindungi seluruh kelompok rute (app) dengan satu berkas _layout.js, lalu menutup siklus dengan logout.

Kebutuhan

  1. Project aplikasi-mahasiswa hasil praktikum Bab 10 — berisi rute app/(app)/mahasiswa/, pemanggilan API, dan BASE_URL.
  2. Backend buku berjalan di http://localhost:3000 (folder backend/; jalankan npm install sekali, lalu npm start).
  3. Expo Go atau emulator Android/iOS, dan Node.js LTS.
  4. Paket expo-secure-store, dipasang pada langkah persiapan.

Persiapan

  1. Buka backend/README.md. Catat dua hal: (a) bentuk request dan respons endpoint /api/auth/register dan /api/auth/login; (b) cara mengaktifkan proteksi rute pada server. Bila middleware proteksi tersedia, aktifkan untuk GET /api/mahasiswa, karena praktikum ini justru menguji bahwa halaman mahasiswa tidak bisa diambil tanpa token.
  2. Pada folder project, pasang penyimpanan aman dengan perintah di bawah.
  3. Mulai server backend dan pastikan endpoint login dapat diakses — membuka alamatnya di peramban sudah cukup untuk melihat gambaran struktur JSON yang dikembalikan server.

Peringatan sensitif versi

Bila respons server berbeda dari asumsi kode di bawah — misalnya nama field — sesuaikan kode dengan backend/README.md. Jangan mengubah server agar cocok dengan slide; yang menyesuaikan adalah kode praktikum.

Langkah kerja

  1. Buat struktur folder utils/, api/, context/, dan screens/ pada folder project bila belum ada.
  2. Tulis utils/tokenStorage.js — pembungkus SecureStore (Kode 1).
  3. Tulis api/client.js — pemanggil API dengan dukungan token (Kode 2). Salin nilai BASE_URL dari praktikum Bab 10; emulator Android memakai http://10.0.2.2:3000.
  4. Tulis context/AuthContext.js — provider autentikasi dan hook useAuth (Kode 3).
  5. Ubah app/_layout.js menjadi layout akar yang membungkus seluruh aplikasi dengan AuthProvider (Kode 4).
  6. Ubah app/index.js menjadi halaman pengarah berdasarkan status autentikasi (Kode 5).
  7. Tulis screens/Login.js (Kode 6), lalu ubah app/login.js agar menampilkan komponen tersebut (Kode 7).
  8. Ubah app/(app)/_layout.js menjadi protected route (Kode 8) — halaman yang sudah ada di dalam (app) otomatis terlindungi.
  9. Tambahkan tombol Keluar pada halaman beranda app/(app)/index.js (Kode 9).
  10. Uji alur lengkap: daftar akun baru → masuk → buka Daftar Mahasiswa → keluar → coba akses langsung /(app)/mahasiswa, yang harus melempar kamu ke /login.

Penjelasan kode

Kode 1 membungkus tiga fungsi SecureStore agar pemakaiannya seragam di seluruh aplikasi. Kunci penyimpanan dibuat konstan (token_mahasiswa_app) supaya tidak salah ketik di tempat lain; modul ini satu-satunya tempat yang mengenal nama kunci tersebut. Bila kebijakan penyimpanan berubah nanti, cukup satu berkas yang diubah.

Kode 2 adalah pemanggil API tunggal: fungsi kirim menyusun header, mengirim fetch, membaca JSON, dan melempar error berisi pesan dari server bila status bukan sukses. Perhatikan baris headers.Authorization = `Bearer ${token}` — di situlah token disisipkan ke setiap permintaan yang membutuhkannya. Memusatkan logika ini menghindari pengulangan di setiap layar sekaligus memudahkan penanganan kesalahan terpusat, misalnya mendeteksi status 401.

Kode 3 memegang tiga status autentikasi. memuat berarti aplikasi sedang membaca token dari SecureStore saat dibuka — penting agar halaman pengarah tidak mengambil keputusan sebelum data terbaca, sehingga layar tidak berkedip. signIn memanggil API, menyimpan token, lalu memperbarui state; signUp hanya mendaftarkan akun; signOut menghapus token dan mengosongkan state. Hook useAuth melempar error bila dipakai di luar provider — perilaku yang membantu mengenali kesalahan sedini mungkin.

Kode 4 dan 5 membentuk pintu masuk aplikasi. Provider dibungkus di layout akar sehingga semua halaman dapat memanggil useAuth. Halaman pengarah memutuskan arah: status masuk menuju /(app), selain itu ke /login. Keputusan arah hanya dibuat di satu tempat — pola sumber kebenaran tunggal yang menghindari navigasi yang saling bertentangan.

Kode 6 menyatukan dua mode pada satu layar. Validasi di sini tujuannya umpan balik cepat; validasi lengkap dibahas di Bab 8 dan server tetap memvalidasi ulang. router.replace('/') dipakai — bukan push — agar layar login tidak tertinggal di tumpukan navigasi, sehingga pengguna tidak dapat kembali ke sana dengan tombol kembali. Pada mode daftar, setelah sukses aplikasi beralih ke mode masuk; keputusan ini menghindari asumsi bahwa endpoint register langsung menerbitkan token.

Kode 7 menunjukkan pola pemisahan rute dan layar: berkas rute hanya meneruskan ke screens/Login.js. Kode 8 adalah proteksi rute pada kelompok (app): satu berkas _layout.js melindungi Beranda, Daftar Mahasiswa, Detail, dan Formulir tanpa mengubah satu pun berkas halaman — inilah nilai utama pola route group dari Bab 7. Kode 9 melengkapi siklus: tombol Keluar memanggil signOut lalu router.replace('/login').

Hasil yang diharapkan

  1. Saat aplikasi dibuka pertama kali — belum ada token — yang muncul adalah halaman Masuk, bukan Beranda.
  2. Pendaftaran akun baru lewat tab Daftar menampilkan pemberitahuan “Pendaftaran berhasil”, lalu beralih ke tab Masuk.
  3. Login dengan email dan kata sandi yang baru didaftarkan membawa kamu ke Beranda, dengan sapaan “Selamat datang, <nama>” dari respons server.
  4. Halaman Daftar Mahasiswa menampilkan data dari API — berhasil hanya karena token dikirim pada header dan server memproteksi rute tersebut.
  5. Tombol Keluar mengembalikan kamu ke halaman Masuk; upaya membuka /(app)/mahasiswa setelahnya ditolak dan dialihkan ke /login.
  6. Menutup lalu membuka kembali aplikasi tanpa logout membuatmu tetap masuk karena token terbaca dari SecureStore; memasang ulang aplikasi mengembalikanmu ke halaman Masuk karena token tersimpan di area aman perangkat yang ikut dibersihkan.

Salah paham

Kegagalan autentikasi jarang berupa kesalahan logika rumit; yang paling sering adalah alamat server yang salah dan paket yang dipasang dengan perintah keliru. Baca pesan errornya lebih dulu, dan jangan pernah menampilkan kata sandi pada alert atau log saat menelusuri masalah.

Yang harus teramati

  • Layar Login pada pembukaan pertama — sebelum ada token sama sekali.
  • Sapaan nama pengguna di Beranda setelah login berhasil.
  • Penolakan akses ke /(app)/mahasiswa setelah logout, disertai pengalihan ke /login.
  • Tetap masuk setelah aplikasi ditutup dan dibuka tanpa logout, karena token dibaca dari SecureStore.
  • Kembali ke halaman Masuk setelah aplikasi dipasang ulang, karena token tersimpan di area aman perangkat.
Laporan yang baik menyertakan tangkapan layar tiap butir, bukan hanya tulisan “berhasil”.

Kuis kilat

  1. Apa yang menjamin keaslian sebuah JWT?
  2. Kenapa server tetap disebut stateless padahal memakai token?
  3. Kapan keunggulan session paling dibutuhkan?
  4. Fungsi expo-secure-store mana yang menghapus token saat logout?
Kunci kuis kilat
  1. Signature yang dihitung dengan secret key milik server; header dan payload hanya disandikan dengan base64url, bukan dirahasiakan.
  2. Karena verifikasi hanya memerlukan secret key, aritmetika, dan pemeriksaan klaim exp — tidak ada pencarian ke basis data untuk daftar token yang sah.
  3. Saat pencabutan akses harus berlaku seketika, misalnya aplikasi internal perbankan: hapus sesi di server dan akses langsung berhenti.
  4. deleteItemAsync.

Ringkasan bab

  1. Autentikasi membuktikan siapa pengguna; otorisasi menentukan apa yang boleh dilakukan; keduanya berurutan dan diputuskan final di server.
  2. Register dan login adalah dua endpoint REST; kata sandi tidak pernah disimpan polos — server menyimpan hasil hash, dan buku ini tidak pernah menampilkan kata sandi asli.
  3. Session menyimpan state di server: mudah dicabut, sulit diskalakan. Token bersifat stateless: mudah diskalakan, sulit dicabut.
  4. JWT terdiri atas header, payload, dan signature; isinya hanya di-encode sehingga dapat dibaca, sedangkan keasliannya dijamin tanda tangan dengan secret key server.
  5. Klaim exp membatasi umur token; token yang dicuri tetap berlaku sampai kedaluwarsa — solusi umumnya umur pendek plus refresh token.
  6. Protected route di klien memakai Redirect berbasis state autentikasi; keamanan sebenarnya ditentukan proteksi di sisi server.
  7. Token disimpan dengan expo-secure-store — enkripsi Keystore/Keychain — bukan AsyncStorage yang tanpa enkripsi.
  8. Empat prinsip API security: validasi input di server, tanpa secret key di kode klien, HTTPS untuk semua lalu lintas non-lokal, dan least privilege pada izin, klaim token, serta data respons.
  9. Logout dalam arsitektur token berarti menghapus token di klien lalu mengarahkan ulang ke halaman login; server tidak punya sesi untuk ditutup.
  10. HTTP hanya untuk pengembangan lokal; Android memblokir cleartext pada build produksi, dan perilaku Expo Go terhadap HTTP lokal bersifat sensitif versi.
