Subbab 13.1 · deck: “Autentikasi Membuktikan Identitas, Otorisasi Menentukan Hak” & “Peran di SIAKAD Menentukan Apa yang Boleh Dibuka” · buku §13.1

Autentikasi Membuktikan Identitas, Otorisasi Menentukan Hak

Autentikasi adalah proses pembuktian bahwa pengguna benar-benar pihak yang ia klaim; otorisasi adalah proses penentuan hak akses apa saja yang boleh dilakukan oleh pengguna yang identitasnya sudah terbukti. Urutannya selalu tetap: autentikasi lebih dulu, otorisasi sesudahnya. Autentikasi menjawab “siapa kamu?”, sedangkan otorisasi menjawab “apa yang boleh kamu lakukan?”.

Analogi bab ini sederhana dan bertahan lama: saat masuk gedung kantor, petugas membaca kartu identitasmu — inilah autentikasi; setelah identitas terbukti, lencana akses menentukan lantai mana yang boleh kamu masuki — inilah otorisasi. Kartu identitas membuktikan siapa kamu, tetapi tidak otomatis membuka pintu ruang server.

Pada sistem informasi akademik (SIAKAD), perbedaannya terlihat jelas. Saat mahasiswa mengetik email dan kata sandi lalu menekan tombol Masuk, sistem mencocokkan kredensial dengan data yang tersimpan. Setelah terbukti, sistem membaca peran pengguna, lalu menentukan haknya. Peran yang berbeda tetap menjalani autentikasi yang sama; yang membedakan adalah hasil otorisasinya.

Peran di SIAKAD dan yang boleh dilakukan · sumber: deck Bab 13

Di dalam kode, otorisasi biasanya muncul sebagai pemeriksaan seperti “jika peran pengguna adalah admin, tampilkan tombol tambah data”. Perlu diingat: pemeriksaan di sisi aplikasi hanyalah kenyamanan antarmuka. Keputusan otorisasi yang sesungguhnya harus dijatuhkan oleh server, karena pengguna dapat memodifikasi aplikasi klien — pembahasannya di subbab 13.6.

Salah paham

Salah paham tersering: menganggap “login” sudah mencakup autentikasi dan otorisasi sekaligus. Ujilah dengan pertanyaan ini — kalau kamu sudah masuk sebagai mahasiswa, bolehkah kamu membuka nilai mahasiswa lain? Jawabannya tidak, dan yang melarang bukan login, melainkan otorisasi di server.

Pertanyaan penuntun

Kalau tombol Tambah Data disembunyikan dari mahasiswa, apakah datanya sudah aman? (Jawaban: belum — mahasiswa masih bisa memanggil endpoint POST langsung dengan alat penguji API, dan yang seharusnya menolak adalah server.)

Register dan Login: Dua Endpoint, Satu Tiket Masuk

Login adalah proses pengguna memberikan kredensial — biasanya email dan kata sandi — untuk dibuktikan kebenarannya oleh server. Register adalah proses pembuatan akun baru. Pada backend buku, keduanya disediakan sebagai endpoint REST yang berdiri sendiri.

Kredensial yang salah dijawab server dengan 401 Unauthorized. Arti status itu bagi aplikasi: identitas pengguna belum terbukti, sehingga aplikasi harus mengembalikan pengguna ke layar login — penanganannya di subbab 13.4, bagian 2.

Server buku dijalankan dari folder backend/. Cara lengkapnya sudah dibahas di Bab 10; yang perlu kamu ingat di sini hanyalah bahwa tanpa server berjalan, tidak ada endpoint yang bisa diuji.

Peringatan sensitif versi

Bentuk persis jawaban server — nama field, misalnya token dan user — mengikuti backend/README.md. Bila berbeda, sesuaikan kode pada praktikum, bukan memaksa server menyesuaikan slide.

Pertanyaan penuntun

Apa arti 401 Unauthorized bagi aplikasi? (Jawaban: identitas pengguna belum terbukti, jadi aplikasi harus mengembalikan pengguna ke layar login.)

Subbab 13.2 · deck: “Password Tidak Pernah Disimpan sebagai Teks Polos” · buku §13.2

Password Tidak Pernah Disimpan sebagai Teks Polos

Ada satu aturan keamanan yang tidak bisa ditawar pada sisi server: kata sandi tidak pernah disimpan sebagai teks polos. Server menyimpan hasil hashing — pengacakan satu arah — misalnya dengan algoritma seperti bcrypt, ditambah salt agar dua pengguna dengan kata sandi sama menghasilkan nilai hash yang berbeda.

Sifat satu arah itu penting: dari nilai hash tidak dapat diperoleh kembali kata sandi aslinya. Kebocoran basis data tidak langsung membuka akun pengguna, dan itulah sebabnya aplikasi yang lupa kata sandi mengirim tautan pengaturan ulang, bukan mengirim kata sandi lama.

Di sisi klien, kata sandi juga tidak boleh dicetak ke layar, disimpan, atau dimasukkan ke dalam log. Pada buku ini kata sandi selalu ditulis sebagai placeholder ••••••••, dan konvensi itu dipakai juga di halaman ini.

Pertanyaan penuntun

Kalau kamu lupa kata sandi, kenapa aplikasi mengirim tautan pengaturan ulang, bukan mengirim kata sandimu? (Jawaban: karena server sendiri tidak menyimpannya — yang ada hanyalah nilai hash satu arah.)

Subbab 13.2 · deck: “Tabel 13.1 — Session Menyimpan State, Token Tidak” & “Server yang Mengingat Butuh Tempat Berbagi, yang Stateless Cukup Satu Kunci” · buku §13.2

Session Menyimpan State, Token Tidak

Setelah login berhasil, aplikasi membutuhkan cara untuk “mengingat” bahwa pengguna sudah terautentikasi. Ada dua mekanisme utama, dan keduanya bertolak dari tempat yang berbeda.

Session menyimpan state di server: server membuat catatan sesi, memberikan sebuah session ID kepada klien, dan setiap permintaan berikutnya membawa ID itu untuk dicocokkan. Keunggulannya, sesi dapat dicabut kapan saja. Kelemahannya, server harus menyimpan dan mencari state pada setiap permintaan, sehingga ketika server digandakan, sesi harus dibagikan di antara banyak server.

Token bekerja sebaliknya: server tidak menyimpan apa pun. Setelah autentikasi berhasil, server menerbitkan token, klien menyimpannya, dan setiap permintaan berikutnya menyertakan token itu. Server cukup memverifikasi keabsahannya tanpa mencari catatan di basis data.

Pada aplikasi mobile yang berbicara dengan REST API, pola token lebih lazim: server API dirancang stateless sehingga mudah diskalakan, dan aplikasi tidak bergantung pada cookie peramban seperti aplikasi web.

Pertanyaan penuntun

Kalau aplikasi kampus menambah tiga server API, apa yang harus berubah pada mekanisme session? (Jawaban: sesi harus dibagi antar server, misalnya lewat penyimpanan bersama — inilah biaya infrastruktur yang tidak dimiliki token.)

Subbab 13.3 · deck: “JWT: Tiga Bagian, Dua Titik Pemisah” · buku §13.3

JWT: Tiga Bagian, Dua Titik Pemisah

Ada banyak format token; yang paling populer untuk REST API adalah JWT (JSON Web Token), yaitu tanda akses berbentuk JSON yang ditandatangani. JWT adalah string panjang berisi tiga bagian yang dipisahkan titik.

Ketiga bagian tersebut adalah:

  1. Header — menyatakan algoritma penandatanganan dan jenis token, misalnya {"alg":"HS256","typ":"JWT"}.
  2. Payload — berisi claim (klaim), yaitu pernyataan tentang pengguna: sub (identitas pengguna), nama, iat (waktu diterbitkan), dan exp (waktu kedaluwarsa).
  3. Signature — hasil perhitungan kriptografis dari header dan payload menggunakan secret key yang hanya diketahui server.

Cara membacanya: bagian pertama dan kedua adalah teks yang di-encode dengan base64url — penyandian agar karakter JSON aman disimpan dalam string — sedangkan bagian ketiga adalah tanda tangan. Tanda tangan inilah yang membuat JWT tidak dapat dipalsukan: mengubah satu huruf pun pada header atau payload membuat tanda tangan tidak cocok lagi saat diverifikasi server.

Menulis bentuknya di papan sebagai tiga blok berurutan membantu: token hanyalah satu string panjang dengan dua titik sebagai pemisah, bukan tiga berkas terpisah.

Pertanyaan penuntun

Bagian mana yang membuat token tidak bisa dipalsukan? (Jawaban: bagian ketiga, yaitu signature — header dan payload sendiri hanya disandikan, bukan dirahasiakan.)

Subbab 13.3 · deck: “JWT Bukan Enkripsi” & “Kenapa JWT Membuat Server Tidak Menyimpan Apa pun” & “Harga Stateless: Token yang Dicuri Hidup Sampai exp” · buku §13.3

JWT Bukan Enkripsi, dan Server Tidak Menyimpan Apa pun

Satu kesalahpahaman yang penting diluruskan: JWT bukan enkripsi. Header dan payload hanya di-encode, bukan dirahasiakan — siapa pun dapat mendekode dan membacanya. Konsekuensinya tegas: jangan pernah menaruh kata sandi, nomor kartu, atau data rahasia lain ke dalam payload. Yang dilindungi tanda tangan hanyalah keutuhan dan keaslian token, bukan kerahasiaan isinya.

Fungsi kecil berikut memecah token menjadi tiga bagian, semata-mata supaya kamu dapat mengamati bahwa header dan payload hanyalah teks yang terbaca.

Mengapa JWT disebut membuat server stateless? Karena verifikasi hanya memerlukan secret key dan aritmetika: server menghitung ulang tanda tangan dari header dan payload yang diterima, lalu membandingkannya dengan tanda tangan yang dikirim. Tidak ada pencarian ke basis data untuk memastikan “apakah token ini masih berlaku di sistem kami?” — yang ada hanyalah pemeriksaan tanda tangan dan klaim exp. Server mana pun yang mengetahui secret key dapat memverifikasi token yang sama, sehingga infrastruktur mudah digandakan.

Harga dari stateless adalah kesulitan pencabutan: server tidak punya daftar token yang sudah dicabut, sehingga token yang dicuri tetap berlaku sampai exp tercapai. Pola umum untuk mengurangi risikonya: terbitkan token akses berumur pendek — misalnya 15 menit sampai 1 jam — dan gunakan refresh token berumur panjang untuk menerbitkan token akses baru tanpa meminta pengguna login lagi. Refresh token cukup dipahami sebagai gambaran umum di bab ini; penerapannya ada di bagian Tantangan.

Salah paham

Inilah salah paham nomor satu di bab ini: menganggap JWT “terenkripsi” sehingga aman diisi data apa saja. Ulangi kalimat penutupnya dua kali bila perlu — payload bisa dibaca siapa pun yang memegang token.

Salah paham kedua menyusul: stateless bukan berarti server tidak memeriksa apa pun. Server tetap memeriksa signature dan klaim exp pada setiap permintaan.

Pertanyaan penuntun

Jadi apa bedanya logout pada arsitektur token dengan logout pada session? (Jawaban: server tidak punya catatan untuk dihapus; yang dihapus adalah token di sisi klien.)
