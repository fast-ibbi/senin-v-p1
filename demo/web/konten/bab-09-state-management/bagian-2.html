Context API Bekerja Lewat Tiga Bagian

Context API adalah mekanisme bawaan React untuk membagikan data ke seluruh cabang pohon komponen tanpa menurunkannya satu per satu lewat props. Ia menjawab masalah prop drilling pada subbab 9.2 dengan jalur langsung: nilai berangkat dari penyedianya, lalu dibaca oleh komponen yang membutuhkannya.

Tiga bagian bekerja berurutan, masing-masing dengan satu tugas. createContext membuat wadah beserta nilai awalnya. Provider memasok nilai ke seluruh subtree lewat prop value. useContext membaca nilai itu dari dalam subtree.

Tiga bagian Context API · sumber: deck & buku §9.3
BagianPerannya
createContextMembuat objek context beserta nilai awalnya
ProviderMemasok nilai ke seluruh subtree lewat prop value
useContextHook untuk membaca nilai dari dalam subtree

Isi nilai awal dengan null. Nilai awal bukan hiasan: ia adalah petunjuk yang membuat komponen di luar penyedia mudah dideteksi. Pemeriksaan itulah yang nanti dipakai useCart di subbab 9.4.

Salah paham

Context bukan pengganti props secara umum, melainkan jalur langsung untuk data yang benar-benar lintas wilayah. Menyembunyikan semua nilai ke context membuat komponen sulit dipakai ulang, karena kebutuhannya tidak lagi terbaca dari daftar props.

Pertanyaan penuntun

Kalau context mengubah cara data didistribusikan, apakah cara state disimpan ikut berubah? (Jawaban: tidak; state tetap dideklarasikan dengan useState, context hanya mengubah distribusinya.)

Subbab 9.3 · deck: “Polanya Cuma Tiga Baris: Wadah, Provider, Nilai Awal” · buku §9.3

Polanya Cuma Tiga Baris: Wadah, Provider, Nilai Awal

Berkas context biasanya pendek: satu wadah, satu komponen provider, dan satu state di dalamnya. BahasaProvider memegang state bahasa dengan useState, lalu memasoknya ke semua anak lewat value={{ bahasa, setBahasa }}.

Perhatikan bahwa value membagikan nilai dan fungsi pengubahnya dalam satu objek. Tanpa fungsi pengubah, pembaca hanya bisa menampilkan nilai dan tidak bisa mengubahnya — tombol ganti bahasa tidak akan berbuat apa pun.

Analogi dari buku: provider seperti papan pengumuman yang dipasang di satu lantai. Setiap ruangan di lantai itu — children, sedalam apa pun — bisa membacanya tanpa perlu dioperi kertas.

Salah paham

Meletakkan state di luar komponen provider — misalnya di tingkat modul berkas — membuat nilainya tidak pernah berubah dan tidak memicu render ulang. Context mengubah cara mendistribusikan data, bukan tempat menyimpannya.

Pertanyaan penuntun

Pemakaian nyata context di aplikasi sehari-hari apa saja? (Jawaban: tema terang/gelap, bahasa antarmuka, profil pengguna yang sudah masuk, dan keranjang belanja.)

Subbab 9.3 · deck: “Kapan Context Dipakai, Kapan Justru Dihindari” · buku §9.3

Kapan Context Dipakai, Kapan Justru Dihindari

Context dipakai ketika data dibaca banyak komponen yang berjauhan, ketika data berubah lintas layar, dan ketika prop drilling sudah terasa menyakitkan. Context dihindari ketika data hanya dipakai satu atau dua komponen bertetangga: nilai yang tersembunyi di lingkungan membuat komponen sulit dipakai ulang.

Dua arah keputusan · sumber: deck & buku §9.3
Pakai Context kalauHindari Context kalau
Data dipakai banyak komponen yang berjauhan (tema, bahasa, keranjang)Komponen sulit dipakai ulang karena nilainya tersembunyi
Data berubah lintas layarNilai bisa dibaca jelas dari props yang eksplisit
Data ditulis oleh banyak pihak yang samaData dipakai hanya satu atau dua komponen bertetangga

Satu catatan perilaku yang harus diingat: saat nilai context berubah, setiap komponen yang memanggil useContext pada context itu ikut di-render ulang, tanpa pandang bulu. Untuk data yang jarang berubah — tema atau bahasa — ini tidak masalah. Untuk data yang sering berubah dengan pembaca sangat banyak, aplikasi besar memecah provider menjadi beberapa context kecil.

palet adalah nilai turunan dari mode, dan ia dihitung di dalam provider — bukan di setiap komponen. Dengan begitu aturan warna hidup di satu tempat: menambah mode baru cukup mengubah satu berkas.

Salah paham

Render ulang seluruh cabang bukan cacat. Untuk data yang jarang berubah — tema, bahasa — biayanya tidak terasa. Yang berat adalah data yang sering berubah dengan pembaca sangat banyak, seperti keranjang yang terus bertambah saat pengguna berbelanja.

Pertanyaan penuntun

Kalau seluruh aplikasi dibungkus satu provider raksasa, apa risikonya? (Jawaban: setiap perubahan memicu render ulang semua pembacanya, termasuk yang tidak berkepentingan.)

Subbab 9.4 · deck: “Custom Hook Membungkus State agar Bisa Dipakai Ulang” · buku §9.4

Custom Hook Membungkus State agar Bisa Dipakai Ulang

Custom hook adalah fungsi JavaScript biasa yang namanya diawali kata use, memanggil satu atau lebih hook bawaan di dalamnya, dan mengembalikan data serta fungsi yang dibutuhkan pemakainya. Ia bukan fitur baru React, melainkan pola organisasi kode.

Tiga aturan yang sama dengan Bab 4 tetap berlaku: nama fungsi wajib diawali use; hook bawaan hanya dipanggil di tingkat atas fungsi; dan pemanggilannya tidak boleh berada di dalam percabangan atau perulangan. React melacak urutan pemanggilan hook, sehingga urutan itu tidak boleh berubah antar-render.

Manfaatnya tiga kali lipat: komponen menjadi lebih pendek dan fokus pada tampilan, logika dapat dipakai ulang tanpa menyalin kode, dan logika yang terisolasi lebih mudah diuji — prinsip yang dipakai lagi di Bab 14.

Salah paham

Custom hook tidak boleh dipanggil di dalam if atau perulangan, meskipun isinya terlihat seperti fungsi biasa. Pelanggaran aturan ini membuat urutan hook berubah antar-render, dan React kehilangan pasangan state milik komponennya.

Pertanyaan penuntun

Apakah custom hook menyimpan state-nya sendiri? (Jawaban: tidak; state itu milik komponen yang memanggilnya, sehingga setiap pemanggil mendapat salinan sendiri.)

Subbab 9.4 · deck: “useCart: Satu Pintu ke Context, Layar Tak Perlu Tahu Namanya” · buku §9.4

useCart: Satu Pintu ke Context, Layar Tak Perlu Tahu Namanya

Alih-alih setiap layar memanggil useContext(CartContext) sendiri, kita menyediakan satu hook useCart() yang membungkus akses itu sekaligus memberikan pesan kesalahan yang jelas bila dipakai di luar provider.

Pemeriksaan ctx === null bekerja karena nilai awal context memang null. Pesan useCart harus dipakai di dalam <CartProvider>. jauh lebih mudah ditelusuri daripada “null tidak bisa dibaca” yang samar. Dengan pola ini, komponen tidak pernah menyentuh CartContext secara langsung, sehingga nama dan struktur context bebas diubah tanpa menyentuh layar.

Salah paham

Hook ini hanya bekerja di dalam subtree CartProvider, bukan di sampingnya. Menaruh provider di satu layar membuat layar lain tetap melempar error, meskipun provider sudah “ada” di aplikasi.

Pertanyaan penuntun

Kalau provider dipasang di tempat yang salah, apa yang kamu lihat di layar? (Jawaban: error useCart harus dipakai di dalam <CartProvider>. — error itu pertolongan, bukan gangguan.)

Subbab 9.5 · deck: “Tiga Pertanyaan Menyaring Data yang Layak Global” & “Tangga Keputusan: Berhenti di Tingkat Paling Sederhana” · buku §9.5

Tiga Pertanyaan Menyaring Data yang Layak Global

Setelah semua teknik dikuasai, pertanyaan yang paling praktis justru yang paling awal: kapan sebuah data layak menjadi global state? Tiga pengujian berikut dipakai berurutan, bukan sebagai daftar hafalan.

  1. Berapa pemakainya? Satu komponen berarti state lokal sudah cukup.
  2. Dipakai lintas layar? Ditulis di satu layar dan dibaca di layar lain — data itu layak global.
  3. Banyak pihak menulis data yang sama? Satu tempat mencegah salinan yang saling bertabrakan.

Kebalikannya sama penting untuk dikenali. Ada tiga tanda data tidak perlu global: data yang dapat dihitung ulang dari data lain, data milik server, dan data sementara yang hanya hidup selama satu layar terbuka. Data server sebaiknya diambil dan di-cache oleh satu lapisan khusus (Bab 10 dan 11), bukan disalin mentah ke global state; isi formulir sebelum disimpan cukup menjadi state lokal.

Dari situlah lahir tangga keputusan bab ini: state lokal → lifting state up → Context API → pustaka state management, dengan berhenti di tingkat paling sederhana yang masih memenuhi kebutuhan. Naik satu tingkat hanya ketika ada pemakai baru yang benar-benar membutuhkannya.

Salah paham

Menyimpan nilai turunan membuka pintu ketidaksinkronan: satu operasi yang lupa memperbaruinya sudah cukup merusak tampilan. Nilai seperti totalHarga dan jumlahItem lebih aman dihitung.

Pertanyaan penuntun

Kalau total harga dihitung pada setiap render, apakah aplikasi jadi lambat? (Jawaban: tidak untuk daftar sependek keranjang; optimasi dini belum perlu.)

Subbab 9.6 · deck: “Zustand dan Redux Toolkit: Bukan untuk Skala Kuliah” · buku §9.6

Zustand dan Redux Toolkit: Bukan untuk Skala Kuliah

Context API menyelesaikan masalah distribusi data, tetapi aplikasi berskala besar menuntut hal tambahan: melacak siapa mengubah state dan kapan (devtools), membatasi render ulang hanya pada komponen yang memakai sebagian data (selector), memisahkan logika bisnis dari komponen, serta mempersistensikan state. Dari kebutuhan itulah lahir pustaka state management modern.

Keduanya tidak dipakai buku ini — Context API plus custom hook sudah memadai untuk project kuliah, dan buku menunda pengenalan pustaka sampai kamu benar-benar merasakan keterbatasan Context. Memilih pustaka bukan soal “mana yang terbaik”, melainkan mencocokkan dengan kompleksitas aplikasi dan ukuran tim: Context untuk skala kecil-menengah, Zustand untuk tim yang ingin ringkas, Redux Toolkit untuk aplikasi besar dengan banyak kolaborator.

Salah paham

“Aplikasi profesional selalu memakai Redux” adalah keyakinan yang perlu diberantas. Untuk satu layar yang hanya butuh satu toggle, Redux Toolkit disebut buku ini sebagai kanon untuk menembak nyamuk.

Pertanyaan penuntun

Untuk satu layar yang hanya butuh satu toggle, apakah Redux Toolkit sepadan? (Jawaban: tidak; biaya kode dan kurva belajarnya jauh melampaui kebutuhan.)
