Subbab 9.1 · deck: “Cakupan State Menentukan di Mana Ia Disimpan” · buku §9.1

Cakupan State Menentukan di Mana Ia Disimpan

State adalah data yang berubah karena interaksi pengguna dan memengaruhi tampilan (Bab 4). Bab ini membedakan state berdasarkan cakupan pemakaiannya: siapa saja yang perlu membaca dan mengubah data tersebut.

State lokal hidup di dalam satu komponen dan tidak dibutuhkan komponen lain: teks yang sedang diketik di TextInput pencarian, status buka/tutup panel, atau pilihan ukuran pada satu tombol. State global harus dapat diakses banyak komponen di berbagai cabang pohon komponen, biasanya lintas layar — contoh klasiknya isi keranjang belanja yang tampil di badge layar produk, di daftar layar keranjang, dan nanti di layar pembayaran.

Dua cakupan state · sumber: deck & buku §9.1
CakupanCiri pemakaianContoh
LokalSatu komponen dan anak-anaknyaStatus panel, pilihan satu tombol
GlobalBanyak komponen, biasanya lintas layarKeranjang: badge, daftar, pembayaran

Kenapa perlu dua kategori? Karena ada trade-off antara kesederhanaan dan jangkauan. State lokal sederhana dan mudah ditelusuri, tetapi tidak bisa dibagikan. State global bisa dibagikan ke mana saja, tetapi membawa biaya: lebih sulit dilacak siapa yang mengubahnya, dan perubahan nilainya me-render ulang semua pembaca.

Analogi dari buku: state lokal seperti catatan kecil di meja kerja sendiri, sedangkan state global seperti papan pengumuman kantor — lebih banyak orang terbantu, tetapi isinya harus dirawat dan siapa pun yang menulis di sana harus disiplin.

Salah paham

Global state bukan soal “datanya besar”, melainkan soal luas cakupan pemakainya. Data kecil yang dibaca banyak layar adalah global; data besar yang hanya dipakai satu komponen tetaplah lokal.

Pertanyaan penuntun

Kalau dua layar masing-masing menyimpan salinan keranjang, layar mana yang benar? (Jawaban: tidak ada yang bisa memastikan; di situlah bug dimulai.)

Latihan: Lokal atau Global?

  • B. Isi keranjang yang dibaca layar produk dan layar keranjang

Salah paham

Kesalahan paling sering: menjadikan total harga state terpisah, lalu lupa memperbaruinya pada salah satu operasi. Satu operasi yang lupa sudah cukup membuat tampilan tidak cocok dengan data.

Pertanyaan penuntun

Total harga perlu disimpan, atau bisa dihitung ulang kapan saja dari daftar item? (Jawaban: dihitung ulang — menyimpannya hanya membuka peluang tidak sinkron.)

Subbab 9.2 · deck: “Lifting State Up: State Naik, Data Turun” · buku §9.2

Lifting State Up: State Naik, Data Turun

Lifting state up (menaikkan state) adalah memindahkan state ke komponen induk terdekat yang menjadi “nenek moyang bersama” semua komponen yang membutuhkannya. Induk memegang state, menurunkannya lewat props, dan setiap perubahan dikirim balik lewat fungsi callback.

Kenapa teknik ini ada? Karena aliran data React satu arah: dari induk ke anak. Untuk membuat data “naik”, React memakai pola callback, dan lifting state up adalah penerapan paling sederhananya — cukup untuk kebutuhan dua sampai tiga tingkat komponen. Hasilnya disebut single source of truth (sumber kebenaran tunggal): satu penyimpanan, banyak pembaca, sehingga data tidak mungkin tidak sinkron.

Salah paham

Mahasiswa sering menaruh state di komponen anak lalu “mengirim nilainya ke atas” lewat props. Aliran seperti itu tidak ada di React: data selalu turun, dan perubahan hanya bisa diminta lewat callback.

Pertanyaan penuntun

Kalau state ukuran tinggal di dalam PilihUkuran, bagaimana RingkasanPesanan tahu pilihan pengguna? (Jawaban: tidak akan pernah tahu; karena itulah state dinaikkan.)

Subbab 9.2 · deck: “Lifting State Up Punya Batas: Prop Drilling” · buku §9.2

Lifting State Up Punya Batas: Prop Drilling

Prop drilling adalah mengoper props berantai lewat komponen perantara yang sama sekali tidak memakai data itu. Terjadi saat data harus melewati banyak tingkat komponen. Bayangkan menyampaikan pesan lewat lima orang, empat di antaranya tidak peduli.

  • Menambah satu data baru berarti mengubah seluruh deret perantara.
  • Kode menjadi berisik dan sulit dirawat.

Munculnya prop drilling adalah tanda untuk beralih ke mekanisme berikutnya: Context API. Tapi jangan terburu-buru: lifting state up tetap cukup untuk dua sampai tiga tingkat komponen.

Salah paham

Jangan buru-buru menyimpulkan setiap prop adalah prop drilling. Props eksplisit tetap yang paling mudah dibaca untuk dua atau tiga tingkat.

Pertanyaan penuntun

Gejala apa di kode yang menandakan kita sudah kena prop drilling? (Jawaban: props yang sama muncul di komponen yang tidak memakainya.)

Contoh 1: Induk Menyimpan Ukuran, Dua Anak Membacanya

Contoh lengkap lifting state up berupa tiga file: PilihUkuran (tombol S/M/L), RingkasanPesanan (tabel harga), dan LayarPesan (pemilik state). Versi deck memotong baris judul dan kunci gaya judul; versi utuhnya di buku, dan tiga file itulah yang disalin di bawah.

PilihUkuran menerima dua props — nilai saat ini dan callback. Ketika tombol ditekan, komponen tidak mengubah state sendiri; ia hanya memanggil onPilihUkuran(u) dan menyerahkan keputusan kepada induk.

RingkasanPesanan hanya menerima ukuran dan menghitung harga dari tabel HARGA. Karena pilihan disimpan di induk, komponen ini selalu menampilkan nilai terbaru tanpa tahu bagaimana pilihan itu berubah.

Pertanyaan penuntun

Kenapa onPilihUkuran={setUkuran} boleh ditulis begitu saja? (Jawaban: setter dari useState berbentuk (nilaiBaru) => void, sama dengan kontrak prop callback.)

Subbab 9.2 · deck: “Studi Kasus: Satu Keranjang KRS yang Harus Sama di Dua Layar” · buku §9.7

Studi Kasus: Satu Keranjang KRS yang Harus Sama di Dua Layar

Kasus fiktif dengan pola nyata, pada aplikasi Manajemen Data Mahasiswa (siakad-mobile) yang kamu bangun sejak Bab 5. Layar KRS memilih mata kuliah; layar ringkasan menjumlahkan SKS. Keduanya bukan saudara — induk bersamanya adalah layout akar aplikasi.

Disimpan lokal di layar KRS, pilihan itu tidak pernah sampai ke layar ringkasan. Diangkat ke layout akar lewat props, setiap layar harus meneruskan props yang sama — itulah prop drilling. Jawabannya Context API: satu sumber kebenaran, dua pembaca. Pada project mata kuliah ini, keranjang belanja adalah pilihan KRS, sehingga context-nya bernama KrsContext dan hook-nya useKrs — pola sama persis, hanya nama domainnya yang berbeda.

Pertanyaan penuntun

Kalau layout akar yang memegang state, bagaimana prop drilling bisa dihindari? (Jawaban: dengan Context API — komponen mengambil data langsung dari provider tanpa dioper lewat props.)
