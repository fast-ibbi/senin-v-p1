Bagian 1 — Dari Kode ke Berkas yang Bisa Dipasang

Subbab 15.1–15.4. Bagian ini menutup fase pertama: bagaimana kode JavaScript, aset, dan konfigurasi native dirakit menjadi satu berkas yang bisa dipasang, siapa yang mengerjakan perakitan itu, dan dalam format apa hasilnya keluar. Subbab 15.4 bersifat konseptual dan tidak dipraktikkan.

Subbab 15.1 · deck: “Build Bukan npx expo start” & “Build Development dan Production Bukan Dua Aplikasi Berbeda” · buku §15.1

Build Bukan npx expo start

Build adalah hasil akhir proses kompilasi: kode JavaScript, aset seperti gambar dan font, serta konfigurasi native dirakit menjadi satu berkas yang dapat diinstal pada perangkat. React Native tidak menjalankan kode kita langsung seperti di web — bundel JavaScript dibuat oleh Metro, bundler yang sudah kita kenal sejak Bab 2, lalu digabung dengan kerangka native Android atau iOS.

Selama masa pengembangan, npx expo start menjalankan Metro di komputer kita dan aplikasi di Expo Go atau emulator memuat bundel dari server itu. Setiap perubahan langsung terlihat lewat Fast Refresh. Mode inilah yang disebut development build: cepat, menampilkan pesan error yang kaya, tersambung ke alat debugging Bab 14, tetapi tidak dioptimalkan. Berkasnya besar, lambat, dan bergantung pada komputer pengembang sehingga mustahil dibagikan ke pengguna akhir.

Production build adalah kebalikannya: JavaScript diminifikasi, aset dioptimalkan, bundel disimpan di dalam aplikasi sehingga tidak lagi membutuhkan Metro, dan berkasnya ditandatangani sebagai bukti keaslian. Hasilnya lebih kecil dan lebih cepat, dan itulah yang diunggah ke toko aplikasi.

Development build dan production build · sumber: deck Bab 15, buku §15.1
Aspek Development build Production build
Kecepatan iterasi Cepat, perubahan langsung tampil lewat Fast Refresh Dibuat hanya saat akan rilis atau diuji
Sumber bundel Diambil dari Metro di komputer pengembang Tersimpan di dalam aplikasi, tanpa Metro
Debugging Pesan error lengkap, tersambung DevTools (Bab 14) Diminifikasi, tanpa alat debugging
Ukuran dan kecepatan Berkas besar dan lebih lambat Lebih kecil dan lebih cepat, aset dioptimalkan
Kapan dipakai Setiap hari oleh pengembang dan penguji Saat rilis, pengujian, atau dibagikan terbatas

Trade-off-nya jelas dan disengaja: kemudahan debugging ditukar dengan ukuran, kecepatan, dan keamanan. Pengorbanan itu wajar karena pengguna akhir tidak pernah perlu membaca pesan error internal.

Salah paham

Salah paham paling umum di subbab ini: mengira Expo Go adalah hasil build proyek kita. Expo Go adalah aplikasi milik Expo yang menjalankan bundel dari server pengembangan — bukan berkas hasil build proyek kita. Salah paham kedua: mengira production build adalah “versi lain” aplikasi. Keduanya produk proses build yang sama, hanya tujuannya berbeda.

Pertanyaan penuntun

Kalau Metro dimatikan, aplikasi hasil production build bagaimana? (Jawaban: tetap jalan, karena bundelnya sudah tersimpan di dalam aplikasi.) Lalu mengapa production build tidak menyertakan alat debugging? (Jawaban: pengguna akhir tidak membutuhkannya, dan menyertakannya membuat berkas lebih besar serta startup lebih lambat.)

Subbab 15.2 · deck: “EAS Build: Kerja Beratnya Dipindah ke Cloud” · buku §15.2

EAS Build: Kerja Beratnya Dipindah ke Cloud

EAS (Expo Application Services) adalah kumpulan layanan cloud dari tim Expo untuk membangun, menandatangani, dan mengirim aplikasi. Bagian yang membangun disebut EAS Build. Alasannya praktis: membangun aplikasi Android yang sungguhan memerlukan Android SDK, JDK, dan Gradle, sedangkan membangun iOS memerlukan macOS dan Xcode. Tidak semua laptop di ruang praktikum sanggup memasang beban seberat itu, apalagi macOS dan Xcode untuk iOS.

EAS memindahkan pekerjaan berat itu ke server Expo: kita cukup mengirim kode, server yang mengompilasi, lalu mengembalikan hasilnya beserta tautan unduhan dan kode QR. Analogi yang dipakai deck: EAS seperti jasa percetakan profesional — kamu mengirim desain, hasilnya kembali berupa tautan unduhan, dan mesin cetaknya bukan milikmu.

Alatnya adalah eas-cli, program baris perintah untuk berinteraksi dengan layanan EAS. Ada dua cara memasangnya, dan kita memilih satu cara lalu konsisten menggunakannya sepanjang bab ini.

Cara A memasang alat ini sekali di komputer; setelah itu perintah ditulis eas login, eas build, dan seterusnya. Di Windows, terminal lama kadang tidak mengenali eas setelah pemasangan global — buka terminal baru atau pakai cara B. Cara B tidak memasang apa pun secara permanen, sehingga setiap perintah ditulis dengan awalan npx eas-cli.

Keterangan ini sensitif versi: nama paket, cara pemasangan, dan perintahnya dapat berubah antarvensi, jadi periksa docs.expo.dev saat memasang. Hal yang sama berlaku untuk durasi build, antrean, dan kebijakan paket gratis atau berbayar EAS.

Salah paham

Karena seluruh proyek diunggah ke server, konfigurasi yang keliru ikut terkirim dan hasilnya ikut keliru. Itu sebabnya di praktikum ada langkah pemeriksaan konfigurasi sebelum kode dikirim ke cloud. EAS tidak memperbaiki kesalahan konfigurasi; ia hanya memindahkan tempat kompilasinya.

Subbab 15.2 · deck: “Tiga Profil Build, Tiga Hasil Berbeda” & “eas.json: Pusat Kendali Build” · buku §Contoh 2

Tiga Profil Build, Tiga Hasil Berbeda

Saat eas build:configure dijalankan, EAS memeriksa proyek dan membuat berkas eas.json di folder akar. Berkas inilah pusat kendali build, dengan tiga bagian utama: cli (pengaturan alat itu sendiri), build (kumpulan profil build), dan submit (dipakai saat mengirim build ke toko aplikasi).

Tiga profil build standar · sumber: deck Bab 15, buku §15.2
Profil Kegunaan Hasil di Android
development Pengembangan harian dan modul native development build dengan expo-dev-client
preview Uji calon rilis oleh penguji internal APK (distribution: internal)
production Rilis ke toko aplikasi AAB bertanda tangan, autoIncrement

Nama profilnya sama dengan nama jenis build di subbab 15.1: profil development menghasilkan development build, profil production menghasilkan production build. Ini istilah yang sama, bukan dua hal berbeda. Profil development dipakai bersama npx expo start --dev-client untuk menguji modul native tambahan yang tidak tersedia di Expo Go; profil preview adalah jalur mengirim “beta” ke teman atau dosen tanpa melewati toko aplikasi.

Profil development menghasilkan development build bernama dev client untuk debugging native yang tidak bisa dilakukan di Expo Go. Profil preview menghasilkan APK rilis untuk pengujian internal: distribution: "internal" menandakan build ini dibagikan langsung, bukan ke toko, dan android.buildType: "apk" menegaskan formatnya. Profil production memakai autoIncrement: true sehingga versi mesin dinaikkan otomatis tiap build, dan format keluarannya AAB karena ditujukan ke toko.

Skema eas.json ditandai sensitif versi: kunci seperti cli.version yang ditulis build:configure dapat berbeda antarvensi eas-cli. Jangan hapus bagian cli yang ditambahkan build:configure saat berkas ditimpa dengan versi kita sendiri, dan percayai keluaran build:configure sebagai kebenaran untuk versi yang terpasang.

Pertanyaan penuntun

Profil mana yang kamu pakai untuk mengirim versi beta ke dosen? (Jawaban: preview, karena hasilnya APK yang bisa dipasang langsung tanpa lewat toko aplikasi.) Dan apa yang terjadi kalau versionCode tidak naik pada unggahan AAB kedua? (Jawaban: Google Play menolaknya dengan pesan bahwa version code sudah dipakai.)

Subbab 15.2 · deck: “Urutan Perintah Build Tidak Boleh Ditukar” · buku §Contoh 4

Urutan Perintah Build Tidak Boleh Ditukar

Rangkaian perintah berikut adalah alur kerja standar sebelum build: cek lingkungan, cek konfigurasi, autentikasi, siapkan profil, lalu bangun. Urutannya wajib.

npx expo config --type public adalah jendela mengintip terakhir sebelum kode dikirim ke cloud — bila di sini nama atau application ID salah, hasil build pun salah. npx eas-cli whoami adalah cara termurah memastikan sesi login aktif sebelum menunggu build yang panjang; error pada langkah ini berarti langkah 3 belum berhasil.

Setelah langkah 5, terminal menampilkan tautan build; buka tautan itu untuk mengunduh APK atau memindai kode QR dengan perangkat Android. Build berjalan di server, jadi proses unggah tidak boleh diputus — setelah tahap unggah selesai, laptop boleh ditutup dan hasilnya diperiksa lewat tautan yang sama.

Catatan peka versi

Perintah dan perilakunya dapat berubah antarvensi. Buku menandai bagian ini sensitif versi dan menyarankan menjadikan teks bantuan npx eas-cli --help sebagai sumber kebenaran untuk versi yang sedang terpasang.

Salah paham

Mengira build bisa dijalankan sebelum memeriksa konfigurasi karena “nanti bisa diperbaiki”. Build yang sudah selesai di server memakan waktu dan kuota; kesalahan nama atau application ID di langkah 2 akan terbawa utuh ke hasil build, dan memperbaikinya berarti membangun ulang dari awal.

Subbab 15.3 · deck: “APK Bisa Dipasang, AAB Harus Lewat Play” & “Kenapa AAB Ada: Satu File, Banyak APK” · buku §15.3

APK Bisa Dipasang, AAB Harus Lewat Play

Android memiliki dua format berkas yang sering tertukar. APK (Android Package) adalah berkas aplikasi klasik: satu arsip berisi kode terkompilasi, aset, manifest, dan tanda tangan, yang dapat diinstal langsung pada perangkat — inilah berkas yang dibagikan lewat grup chat atau dipasang dari situs mana pun (sideload). AAB (Android App Bundle) adalah format pengemasan untuk toko: satu arsip berisi semua konten aplikasi tanpa dioptimalkan per perangkat. AAB tidak dapat diinstal langsung; ia diunggah ke Google Play, dan Google-lah yang menyusun split APK.

Satu split APK hanya memuat kode untuk arsitektur prosesor perangkat itu, hanya grafis untuk kerapatan layarnya, dan hanya terjemahan untuk bahasanya. Efeknya nyata: ukuran unduhan pengguna turun drastis, dan pengguna tidak menerima bagian aplikasi yang tidak akan pernah mereka pakai. Yang merakit split APK adalah Google, bukan pengembang — justru di situ keuntungannya, karena infrastruktur Google lebih tahu kebutuhan tiap perangkat.

Di EAS, keterkaitannya dengan profil build: profil dengan distribution: "internal" (development dan preview) menghasilkan APK karena tujuannya diinstal langsung, sedangkan profil production menghasilkan AAB karena tujuannya toko aplikasi. Sejak Agustus 2021 Google Play mewajibkan aplikasi baru diunggah dalam bentuk AAB; kebijakan format unggahan ini sensitif versi, jadi cocokkan lagi dengan dokumentasi Play Console saat mengunggah.

Pertanyaan penuntun

Kalau AAB tidak bisa dipasang, bagaimana penguji internal mendapat berkas instalasi? (Jawaban: lewat profil preview yang menghasilkan APK.) Bagian apa yang dipangkas dari unduhan pengguna? (Jawaban: kode untuk arsitektur prosesor lain, grafis untuk kerapatan layar lain, dan terjemahan bahasa lain.)

Subbab 15.4 · deck: “Build iOS Butuh Keanggotaan yang Tidak Bisa Dilewati” · buku §15.4 · konseptual

Build iOS Butuh Keanggotaan yang Tidak Bisa Dilewati

Membangun aplikasi iOS secara tradisional mensyaratkan macOS dan Xcode. EAS Build menyediakan server cloud berbasis macOS sehingga build iOS dapat dijalankan dari Windows sekalipun — inilah salah satu nilai jual EAS. Namun ada dua syarat yang tidak bisa dilompati.

Pertama, keanggotaan Apple Developer Program, akun developer berbayar tahunan Apple. Tanpa keanggotaan ini, sertifikat penandatanganan tidak dapat diterbitkan dan build iOS tidak dapat dihasilkan, baik di cloud maupun lokal. Angka biaya pastinya sensitif versi dan harus dicek di situs resmi Apple Developer. Kedua, App Store Connect, portal tempat aplikasi didaftarkan sebelum dibangun.

EAS mengelola sertifikat dan provisioning profile — dokumen yang memetakan aplikasi, perangkat yang diizinkan, dan identitas pengembang — secara otomatis, tugas yang sangat membingungkan bila dikerjakan manual di Xcode. Hasil build dapat diuji di TestFlight, saluran uji Apple, sebelum dikirim ke peninjauan.

Perbedaan terbesar dengan Android: tidak ada jalur “instal langsung” yang bebas. iOS hanya mengizinkan distribusi melalui App Store, TestFlight, atau build development ke perangkat terdaftar. Bagi kita yang belum memiliki akun berbayar, memahami alurnya sudah cukup; praktikum bab ini memakai jalur Android.

Salah paham

Mengira build iOS mustahil tanpa laptop Mac. Server macOS EAS menghapus syarat perangkat itu, tetapi tidak menghapus syarat keanggotaan Apple Developer Program. Yang tidak bisa dilewati bukan komputernya, melainkan akun berbayarnya.
