Subbab 4.1 · deck: “Kenapa React Perlu Ada?” · buku §4.1

Kenapa React Perlu Ada?

Sebelum React, pengembang web menulis UI secara imperatif: serangkaian perintah “ambil elemen ini, ubah teksnya, tambahkan baris itu” yang menebar di banyak tempat. Makin besar aplikasi, makin sulit melacak kondisi layar: satu data berubah tetapi lima bagian layar tidak ikut diperbarui karena perintahnya terlewat.

React lahir (2013, dikembangkan Meta) untuk menyelesaikan masalah ini dengan pendekatan sebaliknya, yaitu deklaratif: kita cukup mendeskripsikan apa yang tampil berdasarkan data, dan React yang memutuskan bagaimana memperbaruinya. Analoginya: imperatif itu seperti memberi sopir daftar belokan satu per satu; deklaratif itu seperti menulis alamat tujuan lalu membiarkan sopir memilih jalannya.

Salah paham

Deklaratif sering dianggap berarti “tidak menulis logika”. Yang berpindah hanya tempat logikanya (dari perintah pembaruan layar menjadi deskripsi tampilan), bukan jumlahnya.

Subbab 4.1 · deck: “UI = f(state)” · buku §4.1

UI = f(state): Tampilan adalah Fungsi dari State

Prinsip inti React dirumuskan sebagai UI = f(state): tampilan adalah fungsi dari state (keadaan). Setiap kali state berubah, React menghitung tampilan baru secara otomatis dan memperbarui bagian layar yang benar-benar berubah saja. Sambungkan dengan istilah fungsi dari Bab 3: component menerima data lalu mengembalikan tampilan, persis seperti fungsi yang menerima argumen lalu mengembalikan nilai.

Mekanisme pembandingannya disebut reconciliation (rekonsiliasi/pencocokan) — cukup dipahami sebagai gagasan, tidak perlu dihafal detailnya: React menyimpan gambaran tampilan (virtual), membandingkannya dengan gambaran sebelumnya, lalu menerapkan perbedaan (diff) yang minimal ke layar.

Pertanyaan penuntun

Kalau state tidak berubah tetapi layarnya berubah juga, apa yang salah? (Jawaban: ada yang mengubah data di luar state, misalnya isi array diubah langsung.)

Subbab 4.2 · deck: “Component: Satuan Terkecil Antarmuka” · buku §4.2

Component: Satuan Terkecil Antarmuka

Component adalah fungsi JavaScript yang menerima data (props) dan mengembalikan gambaran tampilan. Aplikasi besar disusun dari puluhan component kecil; React modern hanya mengenal function component, bukan class component. Kamu sudah menulis fungsi seperti ini di Bab 3, jadi hambatannya rendah.

Perhatikan: component adalah fungsinya; elemen adalah hasil pemanggilannya, yaitu gambaran tampilan. <Text> adalah component bawaan React Native (dibahas di Bab 5); di web, <p> biasa boleh ditulis langsung. Component di atas belum muncul di layar sampai diimpor dan dipakai oleh component induk — App.js di akar project adalah root component, pintu masuk seluruh tampilan.

Pertanyaan penuntun

Apa bedanya component dan elemen? (Jawaban: component adalah fungsinya, elemen adalah hasil pemanggilannya.)

Subbab 4.2 · deck: “Enam Aturan Menulis JSX” · buku §4.2

Enam Aturan Menulis JSX

JSX (JavaScript XML) adalah sintaks mirip markup yang dikompilasi menjadi pemanggilan fungsi JavaScript. Karena itu ia punya aturan yang berbeda dari HTML biasa. Mulailah dari dua aturan yang paling sering membuat error di praktikum: camelCase dan satu elemen akar.

  1. Satu elemen akar. Component harus mengembalikan satu elemen pembungkus. Untuk beberapa elemen tanpa pembungkus visual, pakai fragment <>…</>.
  2. Semua tag ditutup, termasuk tag yang “sendiri” seperti <Image />.
  3. Atribut ditulis camelCase. Tidak ada class atau for — karena keduanya kata kunci JavaScript — padanannya className (di web) dan style/onPress (di React Native).
  4. Ekspresi JavaScript ditulis di dalam kurung kurawal {'{}'}: variabel, pemanggilan fungsi, operasi.
  5. Komentar ditulis {'/* … */'} di dalam JSX.
  6. Teks harus berada di dalam komponen teks. Di React Native, string telanjang di luar <Text> memicu error “Text strings must be rendered within a <Text> component”.

Salah paham

Kondisi yang membutuhkan if sering membuat mahasiswa menulis if di dalam JSX. Yang dibutuhkan hanya ekspresi (ternary, &&, atau null) — dibahas di bagian 2.

Props: Data Turun dari Induk ke Anak

Props (properties) adalah cara data mengalir dari component induk ke component anak — ibarat parameter fungsi untuk sebuah component. Component anak tidak perlu tahu dari mana datanya datang; ia cukup menerima satu objek mahasiswa lewat props dan menampilkannya. Kurung kurawal di parameter adalah destructuring (Bab 3 subbab 3.6): cara singkat membuka objek props.

Subbab 4.3 · deck: “Props: Hanya Baca, Nilai Default, dan children” · buku §4.3

Props: Hanya Baca, Nilai Default, dan children

Pertama, props bersifat read-only (hanya baca): component anak dilarang mengubah nilai props yang diterimanya. Kalau anak boleh mengubah data milik induk, sumber kebenaran datanya menjadi kabur; perubahan data harus diminta kepada pemiliknya.

Kedua, props boleh memiliki nilai default. Di React 19.2, nilai default cukup ditulis di parameter fungsi — defaultProps adalah cara lama. Kalau induk lupa mengirim props, component tetap jalan dengan nilai default, tanpa error.

Ketiga, props punya bentuk khusus bernama children: isi yang ditulis di antara tag pembuka dan penutup component otomatis menjadi prop children. Bentuk ini menjadi dasar komposisi component (dibahas di bagian 2) dan dipakai untuk membangun component wadah seperti kartu atau panel.

Pertanyaan penuntun

Kalau induk lupa mengirim props mahasiswa, apa yang terjadi? (Jawaban: component tetap jalan dengan nilai default, tidak ada error.)

Subbab 4.4 · deck: “State dan useState” · buku §4.4

State dan useState

Jika props adalah data yang masuk dari luar dan tidak boleh diubah, state adalah data internal yang dimiliki component dan boleh berubah seiring waktu. Perubahan state inilah yang memicu re-render. Analoginya: props itu seperti paket dari luar yang isinya tidak boleh dibuka sendiri; state itu seperti buku catatan pribadi yang pemiliknya boleh menulis ulang.

State dideklarasikan dengan hook useState — fungsi bawaan React berawalan use yang “mengaitkan” fitur React ke component fungsi.

useState('Semua') menerima nilai awal dan mengembalikan sepasang nilai: state itu sendiri (kategoriProdi) dan setter-nya (setKategoriProdi). Ketika setKategoriProdi('Informatika') dipanggil, React menyimpan nilai baru, menjalankan ulang component, dan seluruh JSX yang bergantung pada kategoriProdi otomatis menyesuaikan — tanpa satu pun perintah manipulasi tampilan ditulis.

Pertanyaan penuntun

Mana yang boleh diubah component: props atau state? (Jawaban: hanya state miliknya sendiri, dan hanya lewat setter.)

Subbab 4.4 · deck: “Aturan Emas: State Tidak Diubah, tetapi Diganti” · buku §4.4

Aturan Emas: State Tidak Diubah, tetapi Diganti

Aturan emas state adalah immutability (ketidakberubahan): jangan pernah mengubah state secara langsung, karena React tidak melihat state sebagai “berubah”. push mengubah isi array yang sama sehingga referensinya tetap; operator spread membuat array baru sehingga React mendeteksi perubahannya. Operator spread sudah kamu kuasai dari Bab 3 — yang baru hanyalah kebiasaan menyalin dulu sebelum diubah.

Salah paham

Banyak mahasiswa menyimpulkan array tidak boleh diubah sama sekali. Yang dilarang adalah mengubah state, bukan memakai operasi yang mengembalikan nilai baru — map, filter, dan spread justru dianjurkan.

Pertanyaan penuntun

Kalau datanya sudah benar tetapi layarnya tidak berubah, apa tersangka pertamamu? (Jawaban: state diubah langsung, bukan lewat setter.)
