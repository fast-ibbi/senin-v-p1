Praktikum Bab 10 — Menghubungkan Aplikasi ke Server

Satu pekerjaan besar: memindahkan sumber data Aplikasi Manajemen Data Mahasiswa dari konstanta di dalam kode ke server di folder backend/. Empat berkas baru, dua berkas rute yang isinya menyusut jadi satu baris, dan tiga keadaan antarmuka yang harus benar-benar terlihat.

Tujuan praktikum

Setelah menyelesaikan praktikum ini, kamu mampu:

  1. menjalankan server buku di port 3000 dan memverifikasi endpoint dengan peramban;
  2. membuat klien fetch di api/mahasiswa.js untuk lima operasi data;
  3. menampilkan daftar dari API lengkap dengan loading, error, dan empty state;
  4. menghubungkan form tambah/edit ke POST dan PUT;
  5. menghapus data dengan konfirmasi dan memperbarui daftar tanpa muat ulang manual.

Kebutuhan

  • Project Expo SDK 57 hasil Bab 2 (template blank, JavaScript) yang sudah memiliki rute Expo Router dari Bab 7 — khususnya app/(app)/mahasiswa/index.js dan app/(app)/mahasiswa/tambah.js.
  • Node.js LTS (minimal 22) untuk menjalankan server.
  • Server backend buku di folder backend/ yang disediakan repo buku.
  • Tempat menjalankan aplikasi: emulator Android, device fisik, atau iOS Simulator — base URL menyesuaikan subbab 10.7.
  • Tidak ada dependency tambahan: fetch, ActivityIndicator, FlatList, RefreshControl, dan Alert semuanya bagian dari React Native.

Persiapan

  1. Buka terminal di folder backend/, jalankan perintah pemasangan dan server pada blok berikut, lalu tunggu keterangan bahwa server berjalan di port 3000.
  2. Uji server lewat peramban: buka http://localhost:3000/api/mahasiswa. Kamu akan melihat lima mahasiswa baku buku dalam format JSON — bukan pesan “Cannot GET”.
  3. Tentukan target penjalanan aplikasi (emulator, device, atau simulator) dan catat base URL yang sesuai.
  4. Buka project aplikasi dari Bab 7 di editor. Pastikan npx expo start tidak sedang berjalan agar bebas dari konflik.

Catatan versi

Path endpoint (/api/mahasiswa) dan bentuk respons di bab ini mengikuti desain REST baku. Bila backend/README.md yang tiba di repo menentukan hal lain, sesuaikan konstanta API_URL dan normalisasi respons di api/mahasiswa.js — hanya dua titik yang perlu diubah.

Langkah kerja

  1. Buat folder api/ di root project, lalu buat berkas api/mahasiswa.js berisi klien fetch lengkap seperti blok di bawah. Sesuaikan API_URL dengan targetmu.
  2. Buat folder screens/, lalu buat screens/DaftarMahasiswa.js berisi layar daftar yang membaca data dari API.
  3. Buka app/(app)/mahasiswa/index.js dari Bab 7 dan ganti isinya dengan versi perute yang memuat komponen DaftarMahasiswa.
  4. Jalankan npx expo start, buka aplikasi, dan amati daftar mahasiswa yang muncul dari server. Uji pull-to-refresh dengan menarik daftar ke bawah.
  5. Buat screens/FormMahasiswa.js yang mendukung dua mode: tambah (tanpa parameter id) dan edit (dengan parameter id, data diambil dari server lalu mengisi form).
  6. Buka app/(app)/mahasiswa/tambah.js dan ganti isinya agar memuat FormMahasiswa.
  7. Uji alur lengkap: tambah satu mahasiswa, kembali ke daftar, ketuk Edit, ubah nama, Simpan, lalu Hapus dengan konfirmasi.
  8. Uji keadaan galat: matikan server, muat ulang daftar, amati pesan ramah dan tombol “Coba Lagi”. Nyalakan server kembali, ketuk tombol itu, dan pastikan daftar pulih.

Penjelasan kode

api/mahasiswa.js adalah satu-satunya tempat aplikasi berbicara dengan server. Setiap fungsi mengikuti pola yang sama: kirim permintaan, periksa response.ok, lempar Error bila gagal, lalu kembalikan data. Kedua fungsi yang mengirim isi menyertakan header Content-Type: application/json dan body hasil JSON.stringify; tanpa keduanya server tidak akan menerima data dan menjawab 400 Bad Request.

Perhatikan dua kehati-hatian kecil yang mudah terlewat. hapusMahasiswa sengaja tidak membaca body dan mengembalikan true, karena server umumnya menjawab 204 No Content. ubahMahasiswa menangani kemungkinan yang sama lewat pengecekan response.status === 204. Ditambah normalisasi Array.isArray(json) ? json : json.data pada ambilSemuaMahasiswa, klien ini tahan terhadap tiga perbedaan kecil antar server.

screens/DaftarMahasiswa.js mempraktikkan tiga keadaan antarmuka dari subbab 10.6. Keadaan memuat ditangani variabel loading dengan ActivityIndicator; keadaan galat ditangani variabel error berisi pesan ramah plus tombol “Coba Lagi” yang mengulang permintaan; keadaan kosong diperiksa lewat mahasiswa.length === 0. useFocusEffect memuat ulang data setiap kali layar kembali menjadi fokus — inilah yang membuat daftar otomatis segar setelah form menyimpan data. Operasi hapus memakai Alert.alert dengan tombol destructive sebagai konfirmasi, lalu memperbarui state secara lokal dengan filter tanpa memuat ulang seluruh daftar.

screens/FormMahasiswa.js memakai parameter rute: useLocalSearchParams membaca id; bila ada, komponen masuk mode edit, mengambil data dari server, lalu mengisi form. Angkatan dan IPK dikonversi dengan String() saat mengisi form (karena input bertipe teks) dan Number() saat menyimpan (karena server menyimpannya sebagai angka). Tombol Simpan dinonaktifkan dan teksnya berubah selama proses berjalan — kebiasaan yang mencegah duplikasi data karena POST tidak idempoten. Validasi sengaja dijaga minimal karena validasi lengkap sudah dibangun di Bab 8.

Hasil yang diharapkan

  1. Saat aplikasi dibuka pada halaman Daftar Mahasiswa, tampil lima kartu mahasiswa baku — Budi Santoso, Siti Aminah, Agus Wijaya, Dewi Lestari, Rizky Pratama — lengkap dengan NIM, prodi, angkatan, dan IPK. Data berasal dari server, bukan dari kode aplikasi.
  2. Terminal server mencatat setiap permintaan masuk: GET /api/mahasiswa saat daftar dibuka, POST /api/mahasiswa setelah form tambah disimpan, PUT /api/mahasiswa/<id> saat edit disimpan, dan DELETE /api/mahasiswa/<id> saat hapus dikonfirmasi.
  3. Setelah menambah mahasiswa baru, layar daftar menampilkan data itu tanpa kamu menekan apa pun. Setelah edit, nama atau IPK berubah di daftar. Setelah hapus, kartu yang bersangkutan hilang.
  4. Saat server dimatikan lalu daftar dimuat ulang, muncul teks “Data tidak dapat dimuat.” beserta keterangan dan tombol “Coba Lagi”. Setelah server dinyalakan kembali dan tombol ditekan, daftar tampil seperti semula.
  5. Pull-to-refresh menampilkan indikator pemuatan ulang dan menyegarkan data dari server.

Salah paham

“Server sudah berjalan di komputermu, berarti aplikasi pasti menemukannya.” Belum tentu. Emulator Android hidup di jaringan virtual sendiri, sehingga localhost menunjuk emulator itu sendiri, bukan komputermu; 10.0.2.2 disediakan justru untuk menembus batas itu. Periksa base URL lebih dulu sebelum menuduh kode fetch-nya salah.

Yang harus teramati

  • Server berjalan di port 3000 dan terminal mencatat setiap permintaan.
  • Lima kartu mahasiswa muncul dari GET /api/mahasiswa, bukan dari konstanta di dalam kode.
  • State loading terlihat sebentar sebelum data datang.
  • Server dimatikan: muncul state error dengan tombol aksi, bukan layar kosong.
  • Satu data ditambahkan: POST tercatat dan id baru muncul di daftar.
Laporan yang baik menyebut status code yang kamu lihat, bukan hanya tulisan “berhasil”. Butir keempat paling sering hilang — mematikan server adalah cara termurah membuktikan bahwa state error benar-benar ada.

Kuis kilat

  1. Metode HTTP apa yang tepat untuk operasi “Create” pada CRUD?
  2. Status code apa yang menandakan resource baru berhasil dibuat?
  3. Kenapa tombol Simpan perlu dinonaktifkan selama permintaan berjalan?
  4. Base URL apa yang dipakai emulator Android untuk menjangkau komputer host?
Kunci kuis kilat
  1. POST — membuat resource baru di alamat koleksi.
  2. 201 Created — data tersimpan dan respons membawa id baru.
  3. Karena POST tidak idempoten: dua permintaan berarti dua data.
  4. http://10.0.2.2:3000 — localhost menunjuk emulator itu sendiri.

Ringkasan bab

  1. Arsitektur client–server memisahkan aplikasi dari data demi satu sumber kebenaran, keamanan, dan kontrol; harganya adalah ketergantungan pada jaringan dan latensi.
  2. REST memandang data sebagai resource dengan endpoint unik dan bersifat stateless.
  3. Metode HTTP memetakan CRUD: GET membaca, POST mencipta, PUT/PATCH mengubah, DELETE menghapus.
  4. GET aman dan idempoten; POST tidak, sehingga tombol Simpan perlu dinonaktifkan saat proses berjalan.
  5. Status code adalah bahasa bersama: 2xx sukses, 4xx kesalahan client, 5xx kesalahan server.
  6. JSON adalah format tukar utama; objek diserialisasi dengan JSON.stringify dan diurai kembali dengan response.json().
  7. fetch hanya melempar error saat jaringan gagal, sehingga pola if (!response.ok) throw wajib dipakai.
  8. Tiga keadaan antarmuka — loading, error dengan aksi, dan empty — menjaga pengalaman pengguna saat komunikasi jaringan berlangsung.
  9. Base URL mengikuti tempat aplikasi berjalan: 10.0.2.2 untuk emulator Android, IP LAN untuk device fisik, localhost untuk iOS Simulator.
  10. API produksi melindungi diri dengan token pada header Authorization: Bearer <token>; detailnya dibahas di Bab 13.
