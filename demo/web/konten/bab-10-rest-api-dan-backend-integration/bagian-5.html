Studi Kasus: Tiga Sistem, Tiga Angka IPK yang Berbeda

Sebuah kampus menengah memiliki tiga sistem yang berjalan terpisah: aplikasi web akademik berbasis PHP, aplikasi mobile untuk mahasiswa, dan sistem informasi kepegawaian. Setiap kali data mahasiswa berubah — misalnya pembaruan IPK — ketiganya menolak sinkron, dan mahasiswa melihat angka berbeda di aplikasi mobile dan di web.

Akar masalahnya bukan teknologi, melainkan data yang terduplikasi di tiga tempat tanpa satu sumber kebenaran. Solusi yang dipilih adalah satu REST API pusat yang menjadi satu-satunya pintu ke data, sehingga web, mobile, dan kepegawaian sama-sama menjadi client.

Salah paham

“Angka IPK berbeda karena ketiga sistem memakai teknologi yang berbeda.” Bukan itu akarnya. Tiga teknologi berbeda dapat menampilkan angka yang sama persis bila semuanya membaca satu sumber; yang bermasalah adalah data yang terduplikasi tanpa satu sumber kebenaran.

Di situlah materi bab ini berbayar: pemisahan client–server (subbab 10.1) mewujudkan satu sumber kebenaran, dan pemilihan REST (subbab 10.2) memungkinkan tiga client berbeda teknologi berbicara dengan satu bahasa HTTP/JSON.

Titik Kegagalan Tunggal dan Dua Sisi Mitigasi

Satu pintu berarti satu titik gagal: bila API pusat mati, semua sistem kehilangan data sekaligus. Itu harga yang sudah tercatat di tabel bagian 1, dan mitigasinya dipraktikkan di dua sisi sekaligus.

Sisi server menjaga ketersediaan: status code 5xx yang jujur, pengawasan log, dan dokumentasi kontrak pada backend/README.md. Sisi aplikasi menjaga pengalaman pengguna: loading, error dengan aksi, empty state, serta pengulangan yang sopan. Sebelum semua itu diuji, server harus lebih dulu dijalankan — sebagai program terpisah dari aplikasi.

Inilah sebabnya server yang mati adalah alat uji termurah: ia membuktikan apakah keadaan galat benar-benar ada di aplikasimu, atau hanya ada di slide.

API Produksi Hampir Selalu Dijaga

Server pada praktikum bab ini berjalan tanpa autentikasi agar kamu fokus pada mekanisme HTTP. Namun API produksi yang menyimpan data pribadi — nilai, email, data mahasiswa — hampir selalu melindungi diri: tidak semua orang boleh membaca, apalagi mengubah.

Pola yang paling umum adalah token. Setelah pengguna login, server menerbitkan rangkaian karakter unik sebagai tanda pengenal. Permintaan berikutnya menyertakan token itu pada header Authorization dengan format Bearer — “pembawa kartu ini berhak atas akses berikut”.

Bila token tidak ada, salah, atau kedaluwarsa, server menjawab 401 Unauthorized dan aplikasi seharusnya mengarahkan pengguna kembali ke layar login. Untuk sekarang cukup dua hal yang diingat: di mana token disampaikan, dan apa arti 401.

Token Menumpang di Header Setiap Permintaan

Kabar baiknya: pola fetch tidak berubah. Menyertakan token hanya berarti menambah satu entri pada headers — keterampilan yang sudah kamu bangun di bagian 3 langsung terpakai. Yang berubah hanya jawaban server ketika token tidak ada.

Siklus penuh — login, token, permintaan terlindungi, logout — beserta cara menyimpan token dengan aman dibahas di Bab 13. Bagian ini hanya menutup jarak antara “API terbuka” dan “API yang tahu siapa pemanggilnya”.

Kontrak API, Versi, dan Langkah Menuju Project Akhir

Kampus pada studi kasus itu juga belajar dua hal yang tidak terlihat di kode. Pertama, kontrak API harus didokumentasikan — itulah fungsi backend/README.md. Kedua, API versi mendatang sebaiknya diberi nomor versi, agar perubahan tidak memutus client lama.

Dari sini jalan ke depan jelas: pola fetch dan tiga keadaan antarmuka dipakai lagi di Bab 11 saat penyimpanan lokal ditambahkan, dan menjadi butir penilaian Project Akhir pada aspek integrasi API. Latihan yang tersedia — memakai PATCH untuk satu field, membuat layar detail, menyimpan daftar terakhir dengan AsyncStorage — semuanya variasi dari pola yang sama.
