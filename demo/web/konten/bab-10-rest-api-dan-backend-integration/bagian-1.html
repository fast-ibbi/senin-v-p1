Data Statis Tidak Pernah Tahu IPK Sudah Berubah

Di Bab 6–8 seluruh data aplikasi ditulis langsung di dalam kode. Data seperti itu disebut data statis: daftar mahasiswa yang kamu ketik di sebuah berkas JavaScript akan sama untuk semua pengguna, di semua waktu, sampai kamu mengubah kodenya lalu membangun ulang aplikasi.

Aplikasi nyata di dunia Sistem Informasi menuntut data yang dinamis: mahasiswa baru ditambahkan, IPK diperbarui, data yang salah dihapus. Pertanyaan yang menentukan arah bab ini bukan “di mana data disimpan”, melainkan “siapa sumber kebenarannya”. Data pada blok berikut bukan lagi konstanta di dalam komponen, melainkan salinan yang datang dari mesin lain setiap kali aplikasi memintanya.

Kalau IPK Budi diperbarui di kantor akademik, berapa lama sampai perubahan itu terlihat di aplikasi? (Jawaban: tidak pernah — aplikasi memegang salinannya sendiri, dan salinan itu hanya berubah bila kodenya diubah lalu aplikasi dibangun ulang.)

Dua Program Terpisah: Satu Meminta, Satu Menyimpan

Jawaban atas pertanyaan sumber kebenaran itu adalah arsitektur client–server: pemisahan tegas antara pihak yang meminta layanan dan pihak yang menyediakannya. Di aplikasi mobile, client adalah aplikasi React Native Expo yang berjalan di ponsel, sedangkan server adalah program lain yang menyimpan dan mengelola data — pada buku ini berupa server Express di folder backend/ yang berjalan di port 3000.

Analogi yang paling bertahan adalah restoran. Kamu memesan lewat pelayan, dapur mengerjakannya, dan kamu tidak perlu tahu cara dapur bekerja; pelayan itulah API. Yang perlu diingat: client menyusun permintaan dan menampilkan hasilnya, server menyimpan, mengelola, dan menjaga data.

Salah paham

Mahasiswa sering mengira server adalah “bagian dari aplikasi”, lalu heran ketika data tidak muncul padahal aplikasi berjalan normal. Server adalah program terpisah yang harus dijalankan sendiri, dan bisa mati sendiri. Bila lupa menyalakannya, yang muncul bukan data melainkan pesan kegagalan jaringan.

Satu Sumber Kebenaran Ditukar dengan Ketergantungan Jaringan

Ada tiga alasan yang saling terkait mengapa data tidak disimpan di aplikasi saja. Pertama, satu sumber kebenaran: semua pengguna melihat data yang sama, tidak ada versi berbeda di tiap ponsel. Kedua, keamanan dan kontrol: data sensitif tetap berada di server yang dapat dijaga, dicadangkan, dan diatur aksesnya. Ketiga, pembaruan tanpa instal ulang: aturan bisnis cukup diubah sekali di server, lalu semua aplikasi langsung mengikuti.

HTTP: Satu Permintaan, Satu Tanggapan

HTTP (Hypertext Transfer Protocol) adalah bahasa komunikasi antara client dan server. Polanya request–response: client mengirim permintaan, server membalas dengan tanggapan. Permintaan membawa empat hal — method (apa yang ingin dilakukan), URL (alamat yang dituju), headers (keterangan tentang pesan), dan body (isi pesan).

Tanggapan server membawa status code dan body berisi data. Bayangkan formulir pengajuan: kamu menulis maksud permintaan, melampirkan keterangan dan berkas, lalu biro layanan membalas dengan stempel hasil beserta dokumen yang kamu butuhkan. Pada blok kiri berikut, stempel dan keterangan itu belum lengkap — dan server tidak tahu harus berbuat apa.

Dari contoh di kanan, tiga hal dibaca berurutan: header membawa metadata, body membawa data, dan status code menyatakan hasil. Perhatikan juga bahwa respons nyaris sama dengan permintaan; tambahan terpentingnya adalah id yang diterbitkan server — bukti data benar-benar tersimpan.

Pertanyaan penuntun

Pada contoh di atas, dari mana kita tahu isi pesannya berformat JSON? (Jawaban: dari header Content-Type: application/json.)

REST Memandang Data sebagai Resource Beralamat

Di atas HTTP berdiri REST (Representational State Transfer), gaya arsitektur API yang paling umum dipakai aplikasi mobile. REST mengajak kita memandang data sebagai resource — mahasiswa, mata kuliah, prodi — yang masing-masing punya alamat unik bernama endpoint.

Dua alamat yang mirip sering tertukar, dan pertukarannya menghasilkan 404 yang membingungkan. Selain itu REST bersifat stateless: setiap permintaan berdiri sendiri dan membawa semua informasi yang dibutuhkan server, sehingga server mudah ditambah kapasitasnya dan tiap permintaan bisa disimpan sementara.

Mengapa REST, bukan yang lain? Sebelum REST populer, integrasi sistem banyak memakai SOAP dengan amplop XML yang kaku dan berat. REST lahir sebagai reaksi: cukup HTTP biasa, data dalam format ringan, aturan yang mudah dimengerti. GraphQL menawarkan kebebasan memilih field, tetapi REST tetap paling banyak dipakai industri karena kesederhanaan dan kematangannya.

Subbab 10.2 · deck: “JSON: Objek JavaScript yang Dikirim sebagai Teks” · buku §10.2

JSON: Objek JavaScript yang Dikirim sebagai Teks

Data yang dipertukarkan REST umumnya berformat JSON (JavaScript Object Notation): teks yang strukturnya persis objek JavaScript — pasangan kunci–nilai, array, angka, dan string. Field di dalamnya sama dengan dataset baku buku dari Bab 4 sampai Bab 8, sehingga kamu mengenali datanya sendiri.

Mengapa JSON dan bukan XML? JSON lebih ringkas, mudah dibaca manusia, dan — keuntungan terbesar bagi pemrogram JavaScript — JSON adalah “bahasa ibu” JavaScript. Objek diubah menjadi teks dengan JSON.stringify, lalu teks itu diurai kembali menjadi objek dengan response.json(). Bab ini memakai keduanya untuk kebutuhan nyata.
